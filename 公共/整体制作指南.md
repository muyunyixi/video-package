# 整体制作指南

> 本项目（claude.ai 项目「视频生成」）做的是用代码生成的诗词短片。本文收录所有视频共用的东西：项目里有什么、怎么协作、版本号怎么定、每次交付什么、文档怎么维护，以及从做完的片子里沉淀下来、以后沿用的制作规则。
>
> 某一部片子自己的设定、分镜、配乐和改版细节，写在这部片子文件夹里的项目文档和版本记录里，不写在这里。通用规则以本文为准；片子的文档与本文不一致时，按本文执行，并把不一致处记下来。
>
> 这些规则是从已经做完的片子里总结出来的经验，不是边界（2026-10-23 用户：“除了有一些我实在不能碰的雷点，其他的不要限制掉新窗口的发挥”）。不能碰的几条列在《新窗口接手说明》第二节；其余的，新片可以沿用，也可以按自己的目标换做法、换技术，换之前和用户说清楚为什么。
>
> 建立于 2026-10-11（原名《视频制作项目整体规则与概要》，当天改为现名；通用文档不带版本号），修订记录见文末。

## 一、项目概要

- 片子的画面、动效、文字排版和声音全部由代码生成。除字体外不用任何图片、视频或音频素材，不用视频模型；生图模型只作为封面的备用方案（见《文案撰写指南》第 14 节）。
- 内容是诗词：诗句是画面的主角，每一句都注明出处。

## 三、协作方式（2026-10-11 用户定）

- 一律用中文交流、写文档。
- 用户用语音转文字提需求，表述可能不准确。收到一批需求，先整理归纳成条目，写出自己的理解；有疑问的列出来确认，确认之前不改视频。
- 用户的意见是建议和灵感的切入点，不是必须照做的指令：说得对的纳入执行，拿不准的拿出来讨论，有更好的方案直接提出来。
- 每个大版本开工前，对全片逐帧检查，主动找出用户没提到的问题和可以优化的地方，一并列出来确认。
- 目标是流量与美感并存：既要耐看，也要留得住人。

## 四、版本号（2026-10-11 用户定）

- 写作 v大版本.小版本，如 v4.0、v4.1、v5.0。
- 小优化、小需求、改动不多：小版本加一（v4.0 → v4.1）。
- 用户的需求很多，或者做了根本性的改变（结构、时长、技术方案大改等）：大版本加一，小版本归零（v4.x → v5.0）。
- 每一轮开工前先定版本号，写进版本记录；用户指定了的，按用户的。
- 只有交给用户的成片占版本号。过程中发出的试听、预览、截图叫“第 N 稿”，不占版本号，记在所属版本的“过程”里（v3.1 的文档里叫“第 N 版”，如“配乐第八版”，指的是同一回事）。

## 五、每次输出交付什么（2026-10-11 用户定，2026-10-17 改）

2026-10-17 用户：“以后我们输出的时候，只需要输出视频就可以了。额外的文件你直接更新在上下文中，然后上传到 GitHub 中。”所以：

1. **发给用户的只有成片**：单文件版（H.265，一个文件直接可用），规格见第六节。
2. **项目里的文档（“上下文”）在交付前更新好**，与这一版成片一致：该片的项目文档改成这一版的真实状态，版本记录加一条，改到的指南、规范一起改。成片、封面图发给用户，由用户自己保存，项目和 GitHub 仓库里都不放（2026-10-17 用户定；项目工具也写不进二进制文件，实测被拒），不用提醒用户上传。
3. **上传到 GitHub**（2026-10-17 连上）：仓库 `muyunyixi/video-package`（公开）。
   - 目录：根目录的 `CLAUDE.md` 是新窗口接手说明（与项目根目录的《新窗口接手说明》同一份）；`公共/` 放项目根目录的文件（三份规范、`汇文明朝体.otf`、`模板/`）；每部片子一个文件夹，只放代码包（用户：“项目文件夹里只要存代码包就可以了”），解开存放，能在 GitHub 上直接看每个文件、比较两版的差别。片子的 `docs/` 里只有它自己的文档（项目文档、版本记录、稿件），共用的规范不放副本。成片、封面图、渲染出的帧不放进去。
   - 什么时候推：**每发一个版本（版本号变了）提交、推送一次**，一次提交大体就是一个版本；预览、草图不单独推送（2026-10-17 用户：“并不是每一次你给我预览都需要向GitHub提交一次，太频繁了。只需要版本号发生变化的时候”）。版本之间只改了文档或封面的，攒到下一次一起推；用户要求时单独推。例外：接手说明（`CLAUDE.md`）里写错、过时的，改完就推，新窗口拿到仓库链接先读的就是它。
   - 提交说明：首行写成“<片名或公共>：vX.Y 做了什么”，不超过 25 个字，细节写在空一行之后的正文里。GitHub 文件列表里每个文件后面显示的，是最近一次改到它的那次提交的首行，不是文件的说明；文件夹是什么写在 README 里。
   - 署名：提交的作者和提交者用用户的身份（2026-10-17 用户定：`muyun`，GitHub 的隐私邮箱 `19288906+muyunyixi@users.noreply.github.com`，提交算在用户的账号上，个人邮箱不公开；只设在这个仓库里：`git config user.name`、`git config user.email`，不改工作环境的全局设置）。提交说明里不加 Claude 的署名（`Co-Authored-By`、`Claude-Session` 这类行）：2026-10-17 第一次提交用了工作环境默认的身份“Claude”，又加了这两行，GitHub 上的贡献者显示成 Claude，用户没有同意过（“谁允许你私自加署名的？”）；那一次提交按用户的意思保留。
   - 版本怎么找：仓库 README 的“项目状态”表。当前版本就是 `main` 上最新的提交；发下一个版本时，把上一版最后那次提交的编号补进表里（`https://github.com/muyunyixi/video-package/tree/<编号>` 能浏览、下载那一版）。不用标签：工作窗口推不了标签、建不了 Release（2026-10-17 实测都被拒，403），这是会话连 GitHub 的通道的限制，不是用户账号的设置。以后要标签，用户在网页上建（Releases → Draft a new release，输入标签名，Target 选那次提交；Release 还能附文件，每个不超过 2 GiB），或者把会话连到用户的电脑，用那台电脑的 git 推（只传标签，不用搬文件）。
4. **发布文案与封面**：照旧按《文案撰写指南》做。文案的架构 2026-10-13 已由用户定下（该指南 A 章），每次附本期的发布文案，写在该片的项目文档里；封面按该指南 B 章做（2026-10-17 起：代码画的线画，图案和颜色按本片的意象，字由同一组线画出），竖版 1080×1440 和横版 1440×1080 两张 PNG（抖音上传要竖封面、横封面各一张；横版由竖版演变：同一幅画按同一套公式画在更宽、更矮的画布上，字和画里的东西相对中线、相对字的位置不变，见该指南第 7 节；2026-10-23 起不再为横版另做“字后减弱”这类迁就），发给用户。

v4.5 以前（2026-10-11 定）每次发给用户五样：两版成片（单文件版和按卷打成分卷 zip 的高清版）、整体代码包、更新项目里的文档、发布文案与封面；推送到 GitHub 暂缓。

## 六、成片规格（默认）

- 1920×1080，30 fps。
- 声音：48 kHz 立体声；整体响度 −14 LUFS，母带真峰值约 −1.2 dBTP。
- 单文件版：H.265（Main，8-bit，hvc1 标记）+ AAC 160k，两遍编码，体积控制在 29.5 MiB 以内。接缝前后压得细（v4.6 起，8.8）：x265 zones，片尾最后 18 帧从画面还在动的地方起用 QP 21，其中最后 10 帧（静止的那几帧，压缩里多是 B 帧，会把颗粒抹平）用 QP 18，片头前 13 帧用 QP 21；全片平均码率 3050k，多用的码率从其余部分匀出来；脚本 `render/encode_v46.sh`（v5.1 起 `render/encode_v51.sh`，同样的设置加颜色换算）。《字与心事》v4.6：接缝 1.5 倍（高清版 1.4 倍），29.35 MiB；v5.1：接缝 1.4 倍，29.35 MiB。
- **颜色（v5.1 起）**：两版都换算成 BT.709（有限范围），矩阵、色域、传递特性三项都标 BT.709。渲染出的帧是 JPEG，它的 YCbCr 按 BT.601；照原样压、只标 BT.601（色域和传递特性不标）时，认标记的播放器读对，不认标记、按高清默认的 BT.709 读的会偏色（《字与心事》模拟：印章红、灯窗的橙 ΔE 约 7.5，纸和墨 ΔE 1 以内）。换算并标全以后，两种读法都对（ΔE 1 以内）。手机拍的视频都是 BT.709，平台和播放器拿不准时也按它读。
- 高清版＝上传平台用的版本（v5.1 起）：H.264 High，两遍编码，可变码率，AAC 256k，faststart。**码率按片子的实际需要定，不定死数值，也不过度溢出**（2026-10-23 用户：“规则文件里不一定要求码率要在12兆以下……主要是你根据视频的实际需要来控制码率，不要设置的过于溢出就可以了。”）：平台的建议当参考（抖音：1080p、30 帧、8–12 Mbps），画面难压的地方（满屏颗粒、快速运动）让码率临时升上去，简单的地方降下来；平均码率给到平台再压一次后看不出差别为止，再多就是溢出（平台对所有上传都会重新压缩）。网上流传的“超过多少就压得更狠”的数字（6 Mbps、72 MB、8–12、12–16 Mbps）互相矛盾，没有平台公布的标准。首尾接缝要在压缩后的文件上量（8.8）：码率的上限不要卡得太死，接缝前后要有码率可借。《字与心事》v5.1／v5.2：满屏纸纹，最难压的 4 秒 CRF 15 要 47.6 Mbps；实测 12 Mbps 的上传文件比 CRF 15 低 8 dB，模拟平台再压一次后只差 0.25 dB，所以取平均 12 Mbps、maxrate 16M、缓冲 16M：平均 11.9 Mbps，110.8 MB，按秒在 0.2–26 Mbps 之间，接缝 1.7 倍；试过把每一秒卡在 16 Mbps 以内，接缝跳到 2.2–2.4 倍（接缝前后半秒要约 36 Mbps 才能让颗粒逐帧接上）。v5.0 以前是 CRF 15（平均 20.7 Mbps，片头 67 Mbps，195 MB，溢出）。分卷 zip 每卷 27 MiB（.z01、.z02……最后一卷 .zip），MP4 只存储不压缩，文件名标 UTF-8。所有分卷放进同一文件夹，用 Bandizip、7-Zip、WinRAR（Windows）或 Keka、The Unarchiver（Mac）打开 .zip 解压，得到与原文件逐字节相同的 MP4；Windows 资源管理器和 Mac 自带的“归档实用工具”不支持分卷 zip。
- 交付前检查：帧齐全、都能读；两版的时长和响度；H.265 的体积；高清版的平均码率；两版的颜色标记（BT.709 三项）；分卷拼回去与原文件逐字节相同；解码后的首尾接缝不超过前后帧间变化的 2 倍（8.8）。`render/verify_final.py`、`render/verify_seam.py`。
- 发布：上传平台用高清版（码率按片子的需要、参照平台建议，接缝在压缩后的文件上量过）；必须用小文件时用 H.265 单文件版。抖音、小红书都会把上传的视频重新压缩：上传文件的码率高过平台播放的码率很多，观众也看不出差别（上一条的实测）。v5.0 以前的高清版用 CRF 15（每帧都紧跟原片），接缝本来就平（1.4 倍）；v5.1 起按码率压，接缝要量（1.8 倍）。

## 七、技术方案与代码包

参考实现来自《字与心事》，新片沿用，除非另有决定。

- 画面：Remotion 组织时间线，three.js（WebGL）画场景，React 叠文字层。
- 渲染：Playwright 驱动 Chromium（SwiftShader 软件渲染 WebGL），逐帧定位、截图存成 JPEG（质量 95），再用 ffmpeg 编码。
- 声音：Python（numpy、scipy）逐个采样合成乐器、音效和总谱，ffmpeg 做母带。
- 全片的时间表放在一个文件里（《字与心事》是 `src/cues.json`：每个镜头、每个声点的帧号），画面和总谱都从它读。
- 《字与心事》v3.1 至 v4.5 实际用的版本（各版相同）：Node 22；esbuild 0.28.2、react 与 react-dom 19.2.8、playwright 1.56.0；Chromium（Playwright 1194 版）；Remotion 4.0.534（core、player）；three.js r187dev；Python 3、numpy 2.5.3、scipy 1.18.1；ffmpeg 6.1（带 libx264、libx265）；zip。系统字体：Noto Serif CJK SC、Noto Sans CJK SC、Latin Modern Mono。
- 代码包包含：源码、配乐合成、渲染与编码脚本、封面的代码（《字与心事》是 `cover/`，放在影片源码之外，v4.4 起）、这部片子自己的文档（项目文档、版本记录、稿件；共用的规范在项目根目录和仓库的 `公共/`，2026-10-17 起不再放副本）、构建用的第三方源码快照（Remotion、three.js），README 写明环境和从代码到成片的步骤。不含：字体文件（在项目根目录）、渲染出的帧、成片。
- 速度：2 核的云端机器上每帧约 1–6 秒，72 秒的片子整片渲染约 2.5–3 小时；光线追踪的段落（《字与心事》v4.0 的更漏）每帧约 10 秒。同时只开一个渲染进程，两个会互相拖慢；渲染途中做测试渲染，也会让正在跑的渲染慢一倍。
- 工作机器是临时的：换窗口、换机器后，渲染出的帧和中间文件都不在了（v3.1 中途换机器，2170 帧全部重渲）。能长期留下的只有项目里的文档和交给用户的成片、代码包，所以每次输出都附完整代码包，文档要写到能凭它们重建。
- 会话空闲时，工作机器会被回收，后台进程随之停止（盘上已有的文件还在）。整片渲染这类长任务，要一直在会话里盯着进度，直到做完；渲染脚本写成可续渲的（跳过盘上已有的帧），被打断后重新启动接着渲（v4.1：机器在 18:10 左右被回收，渲染停在中途，三个小时后会话恢复才接着渲）。
- 着色器要按 SwiftShader 的执行方式来写（v4.3 实测）：它对每个像素都把 if 的两边各算一遍，但一组像素都离开了一个循环，这个循环就停。所以只有少数像素要做的重活（如只落在水滴上的多次采样），不放进 if，而是写成一开头就能离开的循环（`for (…) { if (k >= n) break; … }`，用不到的像素 n = 0）。《字与心事》v4.3 更漏的水滴拖影与倒影，第一稿写在 if 里每帧 78 秒，改成这样每帧约 10 秒，与原来相当。
- 渲染用冻结的打包文件：先复制一份再渲染（如 `bundle_v31.js`），途中改代码、重新打包不影响正在跑的渲染。
- **每一帧只由帧号决定**（v4.5 补）：画面不依赖前面渲过哪些帧。整片是分段、由几个浏览器分别渲出来的，依赖前一帧的东西会在分段处变样。检查：同一帧连续渲染和单独渲染各出一张，逐像素比对。《字与心事》v4.4 片尾落下的字算出了无效的颜色值，浏览器碰到无效颜色就沿用上一帧的颜色：连续渲染时看不出，单独从第 2212 帧渲起时字是黑的，成片里有 6 帧字突然变黑。
  - 《字与心事》月亮段还有一处不满足（v4.0 起就知道，记在代码包 README 第 2 步里，原因没有查明；v5.5 改月亮段时又碰到）：月亮聚圆、呼气那一下（约 1185–1230 帧），从这一段开头（1115 帧）连续渲染才和成片一致；单独渲，或从 1190 帧起渲，月亮偏亮（月心平均亮度 255 对 236），连 v4.5 当时的打包文件也一样。修好以前，重渲这一段要按原来的分段（1115、1235、1355 各自从段首）连续渲完，中途被看门狗打断续渲的那一段要从段首重渲；渲完拿不该变的帧和成片逐帧比对。
  - 查法：只改了画面的一部分时，拿改动碰不到的区域、碰不到的帧和成片逐像素比对。v5.5 改月亮段的房子时，就是比对房子以外的部分又碰到这一处。动手重渲一段之前，先看代码包 README 里这一段有没有特别的渲法。
- 只重渲受影响的帧时，新帧与旧帧逐像素比对，只换有变化的，换下的旧帧留底。粒子很多的帧，同一份代码渲染两次，也会有零星几个像素不同（半透明粒子的叠加顺序），比对时要和代码改动区分开：只是散落的几个像素，没有成片的区域。

## 八、通用制作规则

以下规则在《字与心事》中确立，后续视频默认沿用；形式不同的片子（例如音乐 MV）按自己的需要取舍，不合适的和用户商量着改。各片用到的数值与实测写在该片的项目文档里（《字与心事》是第三节“版式”、第五节“声音”），每一版的变化记在版本记录里。

### 8.1 文字与排版

- 字体（本系列默认）：汇文明朝体用于诗句、片名、主旨句、署名；Noto Serif CJK SC 用于界面上的时间、状态、日期；Noto Sans CJK SC 用于出处；Latin Modern Mono 用于代码。
- 安全边距按 EBU R95 图形安全区（画面 5%）：1920×1080 上下 54 px、左右 96 px，按实际可见墨迹量，不按文字框量。
- **一行字的对齐边界：汉字按字格，行首行尾的标点按墨迹。**所有字体、所有文字行都适用，横排竖排都一样：
  - 以汉字开头或结尾：把汉字当作一个个占位格，以它所在字格（全角字 1 em 见方）的外缘为界。
  - 以标点开头或结尾：标点没有内容衔接的那一侧的空白不算，以标点的实际墨迹为界。如行尾的“。”“，”“、”“》”、行首的“《”。全角“。”“、”“》”右边大半是空的，算进去整行就会往左偏。
  - 半角字符（数字、拉丁字母）以它的步进为格；行首行尾是半角标点（如 /、.）时，同样只算到墨迹。
  - 居中、左对齐、右对齐都用这样定出的两端边界。
  - v4.0 起明确推广到所有字体：此前只在汇文明朝体的诗句上执行，出处行（思源黑体）行尾“》”右侧的空白没有裁掉，整行看起来偏左。
  - 代码里每行的两端边界由同一个函数给出（字符按字格，标点按墨迹），对齐、内边距、回执、光标都用它，不在各处自己量墨迹。v4.1 查出右上角三行、气泡的内边距、回执和没发出的半句仍在按墨迹对齐，以汉字收尾的差了两三个像素，改由这个函数统一给出。
- **网格排（v4.5 起，2026-10-16 用户定）**：中文横排按网格，任何字体都一样；细则、汇文明朝体的档案、字形尺寸、量法和排字工具见根目录《字体处理规范》。要点：
  - 每个字、每个全角标点各占一个 1 em 的字格，一格接一格往前排，不按字体自己的宽度（字体的宽度可能正好 1 em，也可能略小略大）；
  - 字在格里按墨迹左右居中（开引号、开括号靠右，闭的靠左）；数字、拉丁字母按自己的步进；
  - 再按上一条的两端边界对齐整行；同一组的几行共用一张网格，同一列上下严格对齐；
  - 代码里的中文一字两列，三维场景里的单字贴图按同样的规则放字。
  - 起因（《字与心事》v4.4）：按字体的宽度排，灯火两行首字差 1.3 px、行尾差 1.8 px；用户问两行的标点是不是强行对齐的，考据后改成网格排，用户补充单行也按网格排。
- **行距（2026-10-11 用户定，v4.0 起执行）**：多行文字的行距是字号的 1.35 倍，基线到基线。
  - 字号指成片画面上的像素：1920×1080 的画面里，字的 em 方框（全角汉字的字身）有多高，字号就是多少 px。片中有推镜、缩放时，行距与字号同比变化，比例不变。
  - 特殊设计除外，并在片子的文档里写明：字号不同的几行（标题与正文、引子与结论）、刻意的停顿、分在画面两处的两行。
  - 按基线算，与字体、与每行的字无关；逐行绝对定位时，后一行的基线 = 前一行的基线 + 1.35 × 字号。
  - 换算到其他软件（各家“字号”“行距”的单位不同，比例相同）：
    - CSS：`line-height: 1.35`。
    - Word、WPS：行距选“固定值”，设为 1.35 × 字号（磅），如 20 磅的字设 27 磅。不要用“多倍行距 1.35”：它乘的是字体自带的单倍行高（中文字体通常是字号的 1.3–1.5 倍），结果远大于 1.35 倍。
    - PowerPoint：段落行距选“固定值”，1.35 × 字号（磅）；Keynote：行距选“精确”，同样设。
    - Photoshop、Illustrator：行距（leading）= 1.35 × 字号，单位与字号相同。
    - Figma：Line height 设 135%（按字号算）。
    - 剪映、Premiere 等剪辑软件：“字号”“行间距”是各自的内部单位，与像素不成固定比例。按导出的画面实测：量两行同一位置的基线（或同一个字的墨迹底边）相距多少像素，调到 1.35 × 字身高。
- 竖排文字里的标点居中于字格。竖排诗句按墨迹在画面顶边与出处墨迹顶边之间垂直居中，句末标点按它的墨迹算。
- 底部的出处与署名见 8.2。
- 屏幕层文字（出处、署名、角标）固定在屏幕上，不放在会动的图层上；推镜、视差只作用于画面。
- 片中有聊天界面时：气泡的左右内边距从首尾两个字量起，按上面的对齐边界（汉字从字格量，行首行尾的标点从墨迹量，标点右侧的空白不算）；右对齐的气泡之间、气泡与它下方的回执等附属文字（如“已读”）之间，都按这样定出的右边界对齐；日期分隔行按首尾字格居中（v4.1 起；此前从墨迹量）。气泡的形状（圆角、尾巴）是各片自己的设计，写在项目文档里。
- **界面里图标与文字并排时的垂直居中（v4.0 定）**：图标按它的整个外框居中，连附件一起算（如放大镜的手柄），这是 Material、SF Symbols 等图标体系的做法，看起来“圆”会略高于中线；文字按墨迹居中。不按墨迹重心居中图标。
- **打字光标的位置（2026-10-12 用户定，v4.1 起执行）**：片中所有打字光标用同一条规则：光标的左缘落在插入点上，插入点是前一个字的字格右缘。
  - 汉字的字格是 1 em 见方，字形和格边之间本来就有一点空，所以光标看上去离前一个字有一点距离；拉丁字母、数字的字格是它的步进宽度，格边离字形很近，光标看上去紧贴前一个字母。
  - 与字距无关：字距加在两个字之间，不加在光标前面。
  - 光标前还没有字时，插入点是第一格的左缘；用输入法打拼音时，拼音从插入点写起，光标紧跟最后一个拼音字母。
  - v4.0 的三处光标各偏了一点：开头输入条上的光标比字格右缘多出 0.06 格，打拼音时还多算了拼音贴图两侧的留白；搜索框里“yue”后多空了 3 px；彩蛋代码里的光标往左多站了 1.5–4.5 px，压在前一个引号自己的步进里。

### 8.2 署名（2026-10-11 用户要求写成规范）

片中有两种署名，位置相同、写法分开：诗句的出处（“— 桃子《……》”）和片尾的作者署名（/muyun.）。以后的视频都按这一节来，特殊设计另说。

**共同的位置**

- 固定在屏幕层，不随画面推镜、视差移动。
- 水平：按 8.1 定出的两端边界居中。出处行从短线左端算到行尾“》”的墨迹右缘；作者署名从“/”的墨迹左缘算到“.”的墨迹右缘。“》”的墨迹右缘按 8.3 的方法量看得见的墨迹，不用代码里 canvas 报的字形外框（v4.0 起，原因见 8.3）。
- 垂直：主体下缘落在 95% 线（1080 高时 y = 1026），与右上角第一行到顶边的距离相同。汉字以墨迹底边为准（汉字没有下伸部分）；拉丁字母以基线为准（m、n、u 的下缘），y、g、p、/ 等下伸部分不计，允许伸到线下。

**诗句出处**

- 写法：一道朱红短线，后面是“作者《完整正式题目》”；作者名与书名号之间不加空格。题目用完整正式题目。
- 字体字号：思源黑体（Noto Sans CJK SC）24 px，字距 0.18 em（行尾的字距不算进宽度）；汉字墨迹高约 22 px。
- 短线：朱砂 #C0302C，26×2 px，与文字相距 16 px，竖直方向对准文字墨迹的中线；两种场景都是这个颜色。
- 颜色按署名底下画面的明暗分两套：
  - 亮场（底下是亮的画面，如宣纸）：墨色 #1E1D20，不透明度 85%，字重 400，不加光。
  - 暗场（底下是暗的画面，如夜景）：月白 #EAE6DE，不透明度 85%，字重 300，不加光。
  - 两套都不加柔光、光晕、描边，只靠颜色和 85% 的不透明度与画面分开。（v4.0–v4.7 亮场的字外有一圈宣纸色柔光；v4.7 墨色 74% → 85%、柔光减弱，暗场 50% → 85%；2026-10-23 v5.0 用户：柔光“多此一举”，全部去掉。实测《字与心事》：纸面、聊天记录、回信上去掉前后对比度一样（5.5–8.7 : 1）；柔光看得出的只有暮色水面，去掉后对比度由 3.7–4.2 : 1 降到 3.3–3.9 : 1，仍清楚；电线杆从字后扫过时，压到的字有一两帧黑压黑，不影响阅读。）
  - 两套的切换以署名所在区域的实际画面亮度为准，逐帧量出明暗翻转的那一帧；不按段落粗略划分。硬切处在切的那一帧换；画面是渐变的（入夜、转场里的淡入淡出），两套样式在翻转的那一刻前后交叉淡化 6–8 帧，墨色、不透明度一起渐变，字重在正中那一帧换（v4.0 起）。右上角三行跟着同一套切换。
- 出现与消失：随它所注的诗句出现，淡入 8 帧、淡出 6 帧；同一时刻只出现一条。
- 画面上的文字已经很密时（如滚动的聊天记录），可以不加出处（v4.0 用户提出）。

**片尾作者署名**

- 写法：/muyun.，只写这一个，不加“Coding by …”之类。
- 字体字号：汇文明朝体 28 px，字间加 2 px。小写主体（m、u、n）高约 12 px，斜杠从顶到底约 23 px，与 24 px 的出处汉字看起来一样大：拉丁小写比汉字显小，所以字号大一档，两者是“看起来一样大”，不是数字一样。
- 颜色：墨色 #161519，不透明度 70%（片尾是宣纸底）。
- 出现：随片尾页面以墨渗方式逐字出现（字与字相隔 2 帧，每个字渗开 14 帧），随页面一起淡出。

### 8.3 测量与对齐

- **数值上做到绝对的标准（2026-10-11 用户定）**：位置、间距、对齐都按规则算准，在成片画面上量过；不为了“看起来”去挪位置。看起来不对、实测却是准的（如《字与心事》的“忐忑”显得重心偏低、整行往右下斜，实测是平的），用不改数值的办法补偿视觉，如墨色的浓淡和落点。
- 墨迹边缘用亚像素方法量：每行（量左右时是每列）最深的像素按 50% 墨色覆盖插值；不用固定的明暗阈值，那样细笔画（如 y 的尾尖）会少量一行。
  - 坐标：像素 j 占 [j, j+1)，它的值看作 j + 0.5 处的采样，50% 交点在相邻两个像素中心之间线性插值。少了这 0.5，量出的边会整体偏半个像素（v4.0 补充）。
  - 用亮度（Y）量，不用色差：成片是 4:2:0 色度抽样，颜色的边缘被抹宽了两三个像素。
  - 代码里常用 canvas `measureText` 的 actualBoundingBox 当墨迹边界。Chromium 把它向外取整到整像素：24 px 思源黑体的“》”，右缘报 12 px，字形实际只到 11.1 px，看得见的（50%）边约 10.9 px。大字号、以汉字收尾的行影响在半像素以内；小字号、以标点收尾又要精确居中的（如出处行尾的“》”），在栅格上按本条的方法量看得见的墨迹再排（v4.0 补充：出处行因此偏左过 0.8 px）。
  - 要精确排进网格的字体，字形的尺寸从字体文件读，不用 measureText（“掂”在 80 px 时它报 4…77，轮廓实际是 4.53…76.33，按它居中最多偏半个像素）；做法见《字体处理规范》第四节。
- 以渲染出的画面实测为准，定稿前在渲染出的画面上量。Chromium 实测（v4.5）：水平方向在亚像素上画字（位置差 0.25 px，墨迹也差 0.25 px），只有字带着缩放、旋转时才把起点取整到整像素，所以静止下来的字不要留着 scale(1.0001) 这样的变换；竖直方向总是把基线取整到整像素行（四舍五入，用 translateY 挪也一样），算出来的竖直位置在画面上会差到 ±0.5 px，上下对齐、上下居中只能准到这个程度。
- 按字格对齐的，量字格边：在画面上按上面的方法量出墨迹边，再加上这个字在该字号下的侧边距（字体文件里的步进宽度减去字形外框，可以用 fontTools 读出，按字号换算成像素），就是字格边。
- 三维场景里要对齐屏幕上的元素时，不让单个物体离开它所在的格子；需要错开，就整体平移它所在的那一层。
- **条子拼成的图案（窗棂、格子、框线）**：每根条子以它所在的线为中心画，落在同一条线上的条子才能连成一条直线；整幅图案拼成一条路径、一次填色，交叉处不叠两层（半透明时叠两层的地方会更深）。《字与心事》v5.1：灯笼锦中间的灯笼框画在 0.3／0.7、0.33／0.67 那几条线的内侧，连到外框的条子却以线为中心，两者错开半根条子（片尾书页上的窗影 15 px，亭子窗上 2.5–3.3 px），用户看出“竖排和横排都有点没对齐”；改成都以线为中心后，在成片上量，相接的条子相差不到 1 px。
- **一行字看着歪，先量字，再看字外的东西**：网格排的字在画面上是平的，看着歪，多半是字外的东西在作怪：一头的上方压着深色的东西，那一头就显得高；字行旁边有一道斜的带子（墨点、线、图形排成的），水平的字行就看着往反方向斜。先渲几张测试帧，每张去掉一样东西，看哪一张平了，找到原因再改；改字外的东西（减淡、打散），不挪字。《字与心事》：“雀跃更浓于忐忑，”量下来是平的（七个字的墨迹下缘都在 532–535 px）。v5.1 浓墨溅起的墨点落在“雀跃”上方（比半灰深的像素 1113 个，“忐忑”上方 5 个），用户：“总觉得还是左高右低”，把字行上沿以上的墨点改成干成淡墨；用户仍觉得“向右下倾斜”，v5.2 渲三张测试帧：“忐忑”加深、“忐忑”上下一样淡都仍斜，去掉纸上的墨点就平了——剩下的墨点 78% 在左边、59% 在字行以下，从左下往右上排成一道斜 12–19° 的带子；改成纸上的墨点溅落时是浓墨、0.8 秒内都干成淡墨（0.4 倍，与“忐忑”的淡墨相近），比半灰深的墨点像素 7209 → 134。
- **和字行并排的线：要平就严格平，要斜就明显斜**。差一点就平行（零点几度）的线，在一行行水平的字旁边看着像放歪了，不像有意的斜。《字与心事》v5.1：片尾窗影的斜切和旋转几乎抵消，横条向右上斜 0.57°，用户看出“没有对齐”；改成旋转正好抵消斜切（`rotate(-atan(0.05))`），横条严格水平、与三行字平行，竖条仍斜 8.5°（月光从侧面照进来）。

### 8.4 诗句与阅读

- 诗句汉字不为动效改写；出处使用完整正式题目。
- 逐字形成与合句使用同一基准，最后的标点出现时整行不跳；遮罩不裁字。
- 背景字只用已读诗句或核对过的稿件文字。
- 同一时刻只有一个主要阅读方向；被遮住、过小或严重变形的字不算有效阅读。
- **往字外长的效果不糊住字里的白**：墨渗、晕开、描边、加粗这类让笔画变粗的效果，加到最重时，笔画之间最窄的那道白仍要看得出来；能加多重，按最窄的缝定，不按字的外轮廓定。《字与心事》v5.1：“雀跃”是落浓墨的字，渗开 4.4 时墨在笔画外多出约 7 px，“跃”的足字旁两竖之间 8 px 的缝被填满、“口”大半变黑，“雀”的横画也糊在一起，用户看出“连在了一起”；降到 2.0，缝重新透出，墨在笔画外 4–5 px，仍比同一行的“更浓于”（2 px）浓。

### 8.5 声音

- 始终有清楚可闻的音乐或环境承接，不出现大段静音或尾音提前截断；关键动作时音乐让位，普通手机外放也能听见声点。
- 配乐的整体性不能动（2026-10-11 用户定）：为画面改声音时，不拆动已经成形的旋律、和声与段落。
- **给画面多留时间：插入整拍（2026-10-12 用户提出，v4.1 起）**：一段画面需要更多时间时，不压缩相邻的段落，在两段之间插入整拍（一拍或几拍）。插入的拍用前一个和弦的尾音延长来铺垫，垫着环境声，不出现静音；插入点之后的音乐与画面整体平移，各个音彼此之间的位置不变，仍然卡在拍上。插入后的那一小节是不规整的小节，算在下面“全片最多一两处”里。（《字与心事》v4.1 在 26.0 s 插入一拍，让更漏的第一滴水先被看见、再被听见；只把切入提前 0.4 秒或 0.2 秒，后面的画面就不在拍上了。）
- 配乐按一首歌来写：
  - 全片一个速度；
  - 有清楚的歌曲结构（前奏、主歌、导歌、副歌）；
  - 乐句规整（一般 4 小节），不被镜头切断，旋律跨过镜头继续唱；
  - 故事的大转折就是段落的开头；
  - 不规整的小节只放在刻意屏息的地方，全片最多一两处；
  - 小的画面动作交给音效；带音高的音效要在调里、落在拍上、比旋律轻，不替换旋律；
  - 副歌一句比一句高；前面的句子不必先往下落，可以停在不稳定的音上留着劲，最后一句回到主音。
- **节奏组要规律（2026-10-23 用户提出，《字与心事》v5.0 起）**：
  - 鼓是用来打拍子的。每一段一个鼓型、一个力度，整段不变；段与段之间可以分层（整套／轻版），段内不忽强忽弱、不中途换鼓型。用户：“它至少在同一段或者某些有规律的地方，是不是应该是同样的强度呀。”
  - 鼓型要让人跟得上拍：《字与心事》整套是底鼓第 1、3 拍，军鼓加拍手第 2、4 拍，踩镲八分音符；轻版是同样的位置，底鼓轻、只留拍手、踩镲更轻。低音落在底鼓上。
  - 镲（和压在它下面的大鼓）只放在段落开头。不为画面事件（字落下、转场、某个动作）另加鼓，尤其不加不在拍上的鼓：《字与心事》v4.0–v4.7 一线的字每隔三分之一秒落一个，每个字一记通鼓，和拍子对不上，听起来节奏乱。画面事件交给音效。
  - 刻意的停顿保留，但要少、要写明：《字与心事》是 31.5 秒等不来的那滴水（停两拍）、39.5 秒月圆（一记底鼓后停一拍）、43.5 秒倒数（整小节）；导歌一段一个鼓型，最后一拍军鼓滚奏进倒数。
  - 伴奏层（古筝这类拨弦的音型）：同一个音型在整段里反复，跟着和弦换调；固定音量（《字与心事》每个音 −19 dB，拍点上多 1.5 dB）；声像拉开（左右交替 ±0.6），和正中间的旋律在空间上错开，不靠旋律停下时变响、旋律进来时变弱去让位；密度跟着鼓型（整套十六分音符、轻版八分音符）；不在旋律之前单独露出来。这样它一直隐约听得到，不会“偶尔两秒非常明显，然后其他就好像消失了一样”（用户）。v4.0–v4.7 的古筝每小节换一种走法、只在两段里有、在 9.0 秒单独先露半小节、片名的古筝在 9.4–9.9 秒被截断，用户听成“两秒很突兀，然后突然没了”；改成上面的写法后用户：“现在这版的古筝设计的不错。”
  - 有音高的音效（刮奏、拨一声）按自然的衰减收尾，不在还响着的时候按写死的时长截断。
  - 换掉一个声部的写法（例如把各段零散的音型换成一层统一的伴奏）时，拿旧版逐段对照：旧声部在哪些地方撑着衔接，新写法在那里也要有，不能留下空档。量的时候也按手机外放量（只留 350 Hz–12 kHz）：这时只剩低音的地方，手机上就是一片空白。《字与心事》v5.4：v5.0 的古筝伴奏层在往事一段从 32.5 s 才进来，v4.7 在 31.5 s 由古筝接住“该落的一滴不落”那一秒，这一秒就空了（手机外放 −32 到 −34 dB，前后 −19 dB），用户：“滴漏声结束之后和下一个音频片段之间，是有1秒左右的古筝声音的，所以它就衔接上了”；补回这一秒（同一音型、同一音量）。
  - 吹奏乐器（笛、埙、人声）一句的最后一个音要渐弱收住，像气息用尽：音量在最后零点几秒里减下去，气声跟着减，音高可以微微下沉；句中音和音之间的短收音（几十毫秒）只用来换音，不能用在一句的末尾。《字与心事》v5.3：片尾最后一声笛子只有 0.09 秒的收音，最后 0.02 秒里掉到四分之一后归零，气声一起断，用户：“正常人不是气息会逐渐减弱，有一个渐弱的过程吗？哪怕有一点点就好啊”；改成最后 0.8 秒按 (1 − u)^1.6 渐弱、音高沉 14 音分（`synth.flute_line` 的 `tail`）。
- 手机外放检查（v4.0 起）：用 350 Hz 高通、12 kHz 低通模拟手机扬声器，听一遍、量一遍。只靠低频的重要声点（心跳、撞击）加一层中低频泛音（约 400–1300 Hz，饱和后带通，压在原声下面），手机上才听得到；关键处不要让 5 kHz 以上突然跳高，那是手机外放最响、最尖的频段。改动不能喧宾夺主。
- 循环播放的片子（8.8）：首尾的声音只做 20 ms 左右的收与开，防止接缝处咔哒一声；房间底噪、环境声在片尾延续到与片头同一电平，不整体淡出到无声。
- 声画对位以看得见的动作为准：
  - 逐帧量出动作最明显的那一帧（如跳到最高、落地），声音放在这一帧或晚一两帧，不提前；动画代码里的起始帧往往比看得见的动作早；
  - 画面里看不见的动作，按节奏补位；
  - 同一个动作的几层声音（提示音、水声、乐器）落在同一时刻，不要前后错开。
  - 跟着一段运动的声音（滚动、倒卷、滑过），按画面上每一帧的速度走：动得快时响、密，慢下来变轻、变稀，停住时停；不按动作的起止时间套一个对称的包络。（《字与心事》v4.0–v4.3 彩蛋的回车声按倒卷的 1 秒对称地响、中间最响；画面上的倒卷却是一开始最快、越来越慢，声音听上去晚半拍，又比画面长出 0.2–0.3 秒，v4.4 用户指出后改成跟着速度走。）
  - 一组声音跟着哪个东西动，就在那个东西停下时停；几样东西一起动时，各自的声音只跟各自，不让一个已经停下的东西旁边还响着像是它的声音（v4.5，用户指出：《字与心事》v4.4 片尾，光标先滑到了终点，十二个字落回字盘的声音还在响，“光标回退的结束时间更短”；v4.5 让光标和字一起躺下、和那一下轻拍同时停，之后十二声只跟十二个字落地）。
  - 一跳一跳的读数（快进的时钟、计数）配声音时，一跳一声，放在这一跳第一次显示的那一帧之后 1 帧以内：跳得快就密，慢下来就疏。它是数出来的声音，不是跟着运动的连续声，响度可以跟着音乐走（v4.5：快进的时钟减速时，嘀嗒越来越疏、越来越响，接进倒数的三声秒针；v4.4 的棘轮从每秒 6 下加速到 34 下，读数却停着）。
  - 观众会数的东西（一滴一滴的水、一下一下的心跳），画面与声音一一对应：一次只出现一个，下一个等上一个落定再出现；中间不夹听起来像它的别的声音（v4.0 更漏的第 1 稿：第七滴在第六滴落水前就进了画面，两滴之间还有一声木头“嗒”，都被看成、听成“多了一滴”）。

### 8.6 先定骨架

- 动画开工前先定三样：速度（如 120 拍/分，一拍 15 帧，一小节 2 秒）；段落（各段几小节，每段画面尽量是整小节，故事大转折放在段落开头）；必须卡拍的点（只卡大转折和少数关键动作）。
- 它介于电影配乐（先画面、后音乐）和 MV、卡点视频（先音乐、后画面）之间：音乐始终是一首歌，又不要求每个镜头都切在拍上。
- 诗词微电影里，每段长短服从诗句的阅读时间时，可以先定画面，再用电影配乐的办法补齐；结果标准相同。

### 8.7 做与查

- 先验证关键段落，再贯通全片。
- 以实际观看判断：代码能运行、文件能解码只是基础检查。改过的地方在渲染出的画面上逐帧看；没改的地方与上一版比对，确认保持不变。

### 8.8 首尾循环（v4.0 定）

- 短视频平台会循环播放。片尾不淡出到黑场或静音，而是回到片头：最后一帧画的是片头第 0 帧的前一刻（同一个场景、同一个镜头，动画跑到第 −1 帧），接回开头时看不出接缝。
- 检查：把最后几帧和最前几帧排在一起看，接缝处的帧间变化与片中相邻帧相当；闪烁、呼吸一类的周期动画，最后一帧与第 0 帧落在相邻的相位上；声音见 8.5。
- 压缩以后也要接得上（2026-10-17，《字与心事》v4.6；用户：“连播的时候会闪一下，是不是哪一帧没有对齐？”）。帧本身是对齐的，闪出在压缩：编码器在第 0 帧一定放一个关键帧，整张画重新压；片尾最后几帧却是从前面的画面一帧帧推过来的（《字与心事》是字回字盘的运动），两边压出来的质感不一样，循环到接缝时整张画一下子变了。首尾用同一个画质不够（实测还跳 4–19 倍），要把接缝前后一小段压得足够细，让画面紧跟原片；做法见第六节。
- 所以接缝也在解码后的成片上量：`render/verify_seam.py`，接缝那一步的帧间变化除以它前后几步的中位数，不超过 2（片中别的关键帧作对照）。平台还会再压一次，它的关键帧也落在第 0 帧：我们交出去的文件接缝是平的，平台那边仍可能闪（《字与心事》：上传高清版，抖音不闪，小红书闪）。

### 8.9 画自然的东西（2026-10-12 用户提出，v4.1 起）

- 植物、水、落下和滚动的东西，按它们自己的规律画和动，不只求“看起来像”。查得到的规律先查清楚再画，例如：
  - 植物：叶序按物种来（桃是互生，一节一片、左右交替；不在枝梢对生两片）；枝梢是顶芽，嫩叶贴着枝条收拢；老枝叶少，新梢叶多，越往梢越小。枝上的叶和果随枝梢一起长出来，不另做一段从小长大的动画（v4.2，用户提出）。
  - 重力：同一个场景里只有一个重力，溅起的水珠、落下的果子都按它飞和落（《字与心事》v4.0 的小水珠只按三分之一的重力飞，19 帧后还在空中）。
  - 滚动：转过的角度（弧度）= 走过的距离 ÷ 半径；光从固定的方向来，不随物体转。
  - 成群的东西（鸟群、落花、飞雪）出现和离开要有先后：两三只一起，或一只单独，没有一定的次序；不要整群同时启动、同时淡出，像一张贴图在移动，也不要刻意排成整齐的先后（像台阶）。为了加大幅度而加的多余动作（如先往下沉一下）不要加（《字与心事》v4.1 开头的鸿雁，用户提出）。
  - 云：在原地慢慢聚多、加厚；散开时顺着流动的方向拉开、变淡，不要生硬地突然裂开，也不要无缘无故地从两边汇聚、再各自散开（《字与心事》v4.1 子正第 1 稿，用户说像“几条抹布”）。云遮月以朦胧为美，月亮隐隐约约地透出来。
  - 水滴（v4.3，用户提出）：几毫米的水滴由表面张力拉成球形。空气只在速度很快时把它压扁：雨滴以终速（每秒 6.5–9 米）下落，直径 2 毫米的扁 5%–10%，4–5 毫米的高度只剩宽度的七八成、底部发平；从几厘米、十几厘米高处落下的水滴，压扁只有百分之几，就是球形。刚离开出口时会颤动（一会儿略高、一会儿略扁，4 毫米的每秒四十多次，一两秒才平息），但始终围着球形；上尖下圆的“泪滴形”只在细颈断开的一瞬间有，下落时从来不是，更不是拉长的椭圆。
  - 运动模糊：是快门开着时物体走过的拖影，要真的做成拖影——在曝光时间里多取几个时刻平均，半透明、两头渐淡，高光拉成线——不能把它做进物体的形状里（《字与心事》v4.0–v4.2 把水滴按速度拉长成实心的椭球，看上去就是一滴长形的水）。快门照真实的拍法定：慢镜头里拍水滴用短快门（每帧 1/8 上下），水滴看上去是圆的；电影常用的半帧（180°）会让下半程的水滴变成拖影。
  - 镜面：像镜子的水面映出它上方所有的东西。映出了字，就也要映出落下的水滴、溅起的水柱和水珠：水滴下落时，倒影从水里迎上来，落水那一刻两者相接（《字与心事》v4.3 补上）。
  - 透明的东西（水滴、玻璃；v4.4，用户看封面时问水珠为什么像铁珠，查出）：清水自己没有颜色。正对着看约 98% 的光穿过去，只有边缘一圈以反射为主；水滴是一颗小球透镜，把身后的东西倒过来、缩小了给人看。暗的地方，水滴就是深灰加几笔亮光，配色和金属球一样，能认出它是水的，是里面倒立、清楚的像。所以从它里面穿出去的光线，要和镜头直接看出去的光线看同一个场景，遮挡的先后一样（挡在水面前的墙、立在水面前的字），不能抄近路。《字与心事》v4.0–v4.3 把穿出水滴往下走的光线直接送到了水面上，跳过了立在水面上的诗句：水滴里倒立的诗句只剩上半截，上半个水滴是一块暗的水面，下缘一道平直的边；几乎水平的光线落到了铜壶外面的水面上，照出了天空，在水滴正中留下一道细蓝线。上暗、下亮、中间一条地平线，看上去就是一颗金属球。
- 形状取自然的样子，不用几何化的符号代替：桃子画成带浅沟、小尖、略不对称的圆，不画成机械的心形。
- 衬景从简（2026-10-12、13 用户提出）：背景里的房屋、远山一类宁少勿杂，造型克制。一两栋房子加一道连起来的围墙，好过一排断开的小房子（一块一块、中间夹着黑色的，看起来四不像）；层次两层就够；不要大面积的平涂只配一个小细节（如一大片白墙上只开一个小窗）。房子上的门、窗、灯放在两根柱子之间的开间正中，不压在柱子和别的门窗上（v4.5：《字与心事》灯火段两扇亮着的窗，一扇压进门里，一扇骑在柱子上）。
- 门、窗、墙头照真实的建筑画，先找参考图（v5.5，用户：“我在网上检索了一下，不是有很多可以参照的吗？”）：
  - 外墙上的窗要像窗：有窗框或窗套、有窗棂，开在墙面中段，大小和墙相称。一点点大、贴着屋檐的小方块，看着像天窗（用户：“这个有点像小天窗的感觉了，一点点大，还在高处”）。
  - 门画成门：门扇、门缝、门环；不画成一个黑洞。
  - 墙头、门罩、窗罩上的瓦画成瓦：深灰（黛瓦不是纯黑），有瓦垄、瓦当，上表面受一点光。只是一道平涂的黑线时，近看像描边（用户问：“这黑色线条代表什么？在建筑中是什么逻辑？合理吗？”）。
- 画面里对称的两半（《字与心事》月亮段的南北）：对应的东西以中线为轴左右对齐——房子一样宽、一样高，窗一样大、一样高、各在自己房子的正中，门对门——两边只用略微的样式差别区分（用户：“完全可以左右都对齐吧？只要有略微的样式差异就行了”）。两边的细致程度也一致：一边画出瓦垄、瓦当，另一边就不能只是一道平涂。
  - 高度在渲出的画面上量。量着一样高、看着一边低，就查哪一处显得重：带坡的门罩、宽的瓦檐、厚的积雪都会让一边看着低（用户：“左边的门看上去视觉更低一些……右边的那个屋檐画的太宽了，看上去比左边要低不少”）。墙头、门罩的厚度两边一样；积雪只留薄薄一道，可以高出对面的檐，但不要粗到像把屋檐加粗了。
- 枝条、藤蔓一类的长线条：大致一个方向生长，曲率连续、缓慢变化；不先弯再直，不拆成两段。断开的线条，看的人会自动补全中间缺的部分，两段的曲率、走向对不上，整根就像变了形（《字与心事》v4.1 的桃枝前后六稿，见该片版本记录）。

### 8.10 动画的衔接（v4.5 起）

用户说《字与心事》v4.4 片尾“字落回格子里的动画有点不自然”，重做时总结的几条，连同通读 v4.4 时查出的同类问题：

- 在三维场景里动的东西，用场景自己的空间和镜头来动：透视、景深、灯光都跟着场景走。不在屏幕平面上用旋转、纵向压扁去假装它倒下、躺平（v4.4 的落字就是这样，看上去是一张贴纸在转）。从二维的页面进到三维的场景时，先在页面上按场景的镜头把它摆进透视，再交给场景；交接的那一帧，形状、颜色前后一致（画面暗角、灯光也要算进去）。
- 几样东西各自从一处走到另一处时，路径不无故交叉；要先后走的，顺着观众视线移动的方向一个接一个，镜头也朝那个方向走（v4.5 字回字盘：每个字落到自己那一列的正前方，从右往左一个接一个落下，镜头也从右往左回到原位；第一稿让它们斜着落向左边几列，几张卡片在半空叠在一起）。
- 从一种状态换到另一种（飞 → 落定，一种样式 → 另一种）时，换的那一帧位置、大小、颜色是连续的：
  - 落定的姿势要在落地之前就对准。三只麻雀落上“忐忑”时，飞行最后一点把身体中心放在落点上，落地那一帧却按脚踩在落点上摆，整只鸟往上跳了约 0.18 个身长（v4.5 改）。
  - 两种光晕、两种样式交接时，一个渐出、一个渐入，同时存在一段，不在一帧里互相替换（“红笺小字”入夜时，红光一出现，浅色光晕当帧就没了，电线杆从字后露出来）。
  - 新状态的第一帧就要有东西：子正的印章在 00:00:00 那一帧不透明度从 0 起算，那一帧“子初”已撤、“子正”还没出现，是空的。
- 用缓动曲线驱动一个读得出的数（时钟、计数、进度、距离）时，量每个值停留多久：先慢后快再慢的曲线两头的速度是零，数字会在两头停住（v4.4 的时间快进在 23:59:56 停了 2.2 秒，用户问是不是“时间暂停”，而那时配乐的棘轮正在加速，云也在聚厚）。读数快慢要和画面、声音说的是同一件事。
- 变速的读数（时间快进、慢放）不从停住开始，也不落到停住：从前一段的速度平滑加速，保持最快，再平滑减速到后一段的速度；进出两端的速度与前后两段相等，加速、减速只在进出两段（2026-10-16 用户提出）。最快的速度取音乐节奏的整分（如每个 16 分音符跳一个数），让每一跳都落在拍上；各段的起止放在画面或音乐的转折处，最快的速度按要走完的量解出来。《字与心事》v4.5：26.5 s 起用 5 秒从实时加速，每秒 8 秒保持 8.33 秒，再用 3.67 秒减速到倒数的每拍一秒，正好走完 107.5 秒。
- 画面定格时是水平的：镜头的滚转最后回到 0（v4.4 片名定格时停在 −0.46°，右端高约 8 px）。
